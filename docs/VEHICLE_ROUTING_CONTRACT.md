# 차량 접근·연속 경로 모델 계약

- 상태: fleet 핵심 구현·소형 검증 완료, 실데이터 실행 전
- 작성일: 2026-08-20
- 적용 대상: 강남구 P2 greedy-nearest의 실행 현실성 민감도
- 비적용 대상: 실제 서울시 차량 운영 추정, 최적 VRP, 정책 재튜닝

## 1. 목적

현재 공간 시뮬레이터는 공급지에서 수요처까지의 적재 이동시간은 반영하지만 차량 자체의 위치를
갖지 않는다. 이 문서는 첫 접근 이동과 작업 간 연속 위치를 추가할 때 필요한 최소 계약을
동결한다. 다음 구현은 새로운 정책을 찾는 단계가 아니라, 이미 선택한 공급지 보호 정책의 결과가
차량 실행 제약에서 얼마나 달라지는지 확인하는 **사후 운영모델 민감도**다.

## 2. 현재 코드의 사실

근거 구현은 [`GreedyNearestPolicy.plan`](../src/ddareungi_rearrangement/simulation.py)과
[`simulate_replay`](../src/ddareungi_rearrangement/simulation.py)에 있다.

| 항목 | 현재 동작 | 의미 |
|---|---|---|
| 정책 입력 | 판단 시점의 대여소 재고 사본과 이동 대수 상한 | 시각·차량 상태를 알지 못함 |
| 수요처 순서 | 부족량 내림차순, 대여소 ID 오름차순 | 가장 부족한 곳부터 결정론적 처리 |
| 공급지 선택 | 수요처와 직선거리가 가장 가까운 공급지 | 차량과 공급지 사이 거리는 무시 |
| 작업 수 | `max_actions_per_decision`개 이하 | 차량 수나 순회 가능 횟수가 아님 |
| 출발 | 판단 이벤트 시각에 모든 공급지 재고를 즉시 차감 | 실제 차량 접근·픽업 전 재고가 사라짐 |
| 도착 | 공급지→수요처 거리와 상하차 시간 후 | 적재 구간 지연만 반영 |
| 동시성 | 한 판단에서 만든 모든 transfer가 독립적으로 동시 출발 | 같은 차량의 연속 작업을 표현하지 않음 |
| 차량 지표 | 각 transfer의 적재 이동시간 합 | fleet 경과시간·가동률과 같지 않음 |
| trace | 공급지 유출과 수요처 유입 | 차량 ID·배차·취소·부분 픽업이 없음 |

같은 시각에는 반납과 재배치 도착이 먼저 처리되고, 그다음 정책 판단, 마지막으로 대여 요청이
처리된다. 따라서 판단 시각의 transfer는 같은 시각 대여보다 먼저 공급지 재고를 차감한다.

## 3. 현재 결과의 편향

- **수요처에는 낙관적**: 차량→공급지 첫 접근시간이 없어 자전거가 일찍 도착한다.
- **공급지에는 비관적일 수 있음**: 실제 픽업 전 접근시간 동안 이용할 수 있는 자전거도 판단
  시각에 바로 제거한다.
- **운영능력에는 낙관적**: 세 transfer가 한 차량의 연속 작업인지 세 차량의 병렬 작업인지
  확인하지 않고 모두 실행한다.
- **비용에는 과소계상**: 공차 접근거리와 접근시간이 0이다.
- **가동률은 계산 불가**: 차량별 busy/idle 구간과 작업 종료 위치가 없다.

그러므로 현재 359.2km를 단순히 “실제 총 운행거리”로 해석할 수 없다. 첫 접근거리만 사후에
더하는 방식도 픽업 시각과 공급지 요청 결과가 바뀌는 문제를 해결하지 못한다.

## 4. 명칭 충돌 정리

초기 프로젝트 계획은 P3를 `Forecast + min-cost flow`, P4를 `Forecast + VRP`로 정의했다.
현재 보고서는 donor reserve 7 확장을 P3라고 불러 계획 문서와 명칭이 충돌한다.

다음 구현부터 명칭을 아래처럼 사용한다.

- `P2-S`: 기존 서비스형 greedy-nearest, donor reserve 5
- `P2-R`: 공급지 보호형 greedy-nearest, donor reserve 7
- `P2-R-Fleet`: P2-R의 정책 선택은 유지하고 차량 실행 제약만 추가
- `P3`: 향후 수요예측 + 최소비용 흐름을 구현할 때 사용
- `P4`: 향후 예측 + 차량경로 최적화를 통합할 때만 사용

기존 보고서 파일과 과거 커밋의 P3 표기는 재현성을 위해 일괄 변경하지 않는다. README나 새
보고서에서는 `기존 보고서 P3, 이후 명칭 P2-R`로 연결한다.

## 5. 대안 비교

| 대안 | 반영 범위 | 장점 | 한계 | 결정 |
|---|---|---|---|---|
| 고정 접근 페널티 | transfer마다 고정 시간·거리 추가 | 구현이 작음 | 차량 위치·동시성·픽업 재고를 못 고침 | 제외 |
| 영속 fleet 실행기 | 차량별 위치·busy 상태, 접근·픽업·배송 | 정책과 실행을 분리하고 핵심 편향을 고침 | 초기 위치는 합성 가정 필요 | **채택** |
| 완전 VRP | 여러 작업을 한 경로로 공동 최적화 | 운영 현실성이 가장 높음 | 정책 자체가 바뀌고 P4 범위가 됨 | 보류 |

## 6. PM 권고 최소 계약

### 6.1 정책과 실행의 분리

`GreedyNearestPolicy`는 현재처럼 공급지·수요처·희망 이동 대수를 담은 transfer intent만 만든다.
새 fleet 실행기는 intent를 실제 차량에 배정하고, 접근 후 픽업 가능한 수량을 확정한다. 차량
제약 때문에 실행되지 않은 intent가 정책 실패인지 차량 부족인지 구분되도록 한다.

기존 `simulate_replay(scenario, policy)`의 결과는 바꾸지 않는다. 새 경로는 명시적으로 fleet
설정을 넘긴 별도 실행에서만 활성화해 25개 기존 회귀 테스트와 과거 보고서를 보존한다.

### 6.2 차량 수

프로젝트 계획에 이미 기록된 1·2·3대를 모두 실행한다. 3대를 “실제 보유 차량”으로 주장하지
않고, 기존 시간당 최대 3개 작업과 비교하기 위한 합성 시나리오로만 사용한다.

- fleet 1: 한 판단 시점에 최대 1개 작업
- fleet 2: 한 판단 시점에 최대 2개 작업
- fleet 3: 한 판단 시점에 최대 3개 작업
- 바쁜 차량은 다음 판단에서도 사용할 수 없음
- 판단 사이에 차량이 한가해져도 다음 정시 판단 전에는 새 작업을 받지 않음

### 6.3 초기 위치

공식 차고지·교대 시작 위치 데이터가 없으므로 대여소 좌표로 만든 결정론적
`greedy medoids`를 합성 전략 거점으로 쓴다. 전체 거리합이 최소인 첫 대여소를 고르고, 이후
현재 최근접 거리합을 가장 많이 줄이는 대여소를 하나씩 추가해 차량 ID 오름차순으로 배정한다.

- 관측값이 아니라 `synthetic_strategic_staging`으로 저장
- 같은 좌표 입력이면 항상 같은 대여소를 선택
- 동률은 대여소 ID 오름차순으로 해소
- 현재 공급지 즉시 출발 결과는 별도 `instant_at_donor` 낙관 하한으로 유지
- 실제 차고지 정보가 생기면 초기 위치만 교체할 수 있어야 함

### 6.4 배차와 이벤트 순서

1. 기존 우선순위대로 같은 시각의 반납·배송 도착을 먼저 처리한다.
2. 정시 판단에서 P2-R이 최대 3개의 transfer intent를 만든다.
3. idle 차량만 후보로 두고 intent 순서대로 공급지까지 가장 가까운 차량을 배정한다.
4. 동률은 접근거리, 차량 ID 순서로 해소한다.
5. 배차 시점에는 공급지 재고를 차감하지 않고 `vehicle_dispatch`만 기록한다.
6. 접근 후 `relocation_pickup` 이벤트에서 현재 공급지 재고를 다시 확인한다.
7. 실제 픽업 수량은 `max(0, min(희망량, 차량용량, 현재재고 - donor reserve))`다.
8. 픽업이 0대면 작업을 취소하고 차량은 공급지에서 idle 상태가 된다.
9. 양수면 그 시각에 공급지 재고를 차감하고 자전거를 in-transit으로 옮긴다.
10. 적재 이동시간과 기존 대당 상하차 시간을 더한 뒤 수요처에 도착한다.
11. 배송 시 수요처 재고를 늘리고 차량 위치를 수요처로 갱신한 뒤 idle로 전환한다.
12. 분석 종료 때 depot으로 강제 복귀시키지 않는다.

차량은 한 번에 한 작업만 수행한다. 서로 다른 차량의 작업은 병렬일 수 있지만 같은 차량의
busy 구간은 겹칠 수 없다.

### 6.5 거리·시간

- 접근거리: 차량 현재 위치→공급지 Haversine × 1.3
- 적재거리: 공급지→수요처 Haversine × 1.3
- 이동속도: 기존 비교와 같은 20km/h
- 차량용량: 기존 비교와 같은 10대
- 처리시간: 기존과 같은 이동 대수 × 0.75분을 배송 소요시간에 포함
- 총거리: 접근거리 + 적재거리
- 차량 busy 시간: 접근시간 + 적재시간 + 처리시간

실제 교통·신호·근무교대·휴식·차고지 복귀는 이 단계에서 추가하지 않는다.

## 7. 새 상태와 지표

### 차량 상태

- `vehicle_id`
- `station_id` 또는 현재 위치 좌표
- `available_at`
- `status`: idle, approaching, delivering
- `current_job_id`

### 운영 지표

- `transfer_intents`
- `jobs_dispatched`
- `jobs_cancelled_no_vehicle`
- `jobs_cancelled_no_surplus`
- `planned_bikes`와 `picked_up_bikes`
- `pickup_shortfall_bikes`
- `approach_distance_km`
- `loaded_distance_km`
- `total_vehicle_distance_km`
- `approach_minutes`, `loaded_minutes`, `handling_minutes`
- 차량별·전체 `busy_minutes`와 `utilization_rate`
- 분석 종료 시 busy 차량 수와 운송 중 자전거 수

기존 `relocation_distance_km`와 `relocation_vehicle_minutes`는 과거 보고서 호환을 위해 의미를
바꾸지 않는다. fleet 실행 보고서에서는 분해 지표와 총합을 새 열로 저장한다.

## 8. 평가 계약

- 정책: P2-R, donor reserve 7 고정
- 정책 파라미터: 하한 2, 목표 5, 상한 8, 적재 10대, 속도 20km/h
- 실행 시나리오: 기존 `instant_at_donor`, fleet 1·2·3
- 초기 위치: fleet별 합성 greedy medoids
- 요청·대여소·초기 재고: 기존 165개·16,205건 홀드아웃과 동일
- 비교 지표: 실패, 구제·악화, p10, 악화 대여소, 빈 시간, 이동 대수, 접근·적재·총거리,
  차량 busy 시간
- donor reserve나 정책 후보를 다시 학습하지 않음
- 같은 홀드아웃을 재사용하므로 `post_hoc_execution_model_sensitivity`로 표시하고 독립 검증으로
  부르지 않음

fleet 1·2·3 중 하나를 실제 권고안으로 자동 선택하지 않는다. 공식 차량 수·교대·차고지 정보가
없어 이 단계의 목적은 성능 범위를 보여주는 것이다.

## 9. 구현 합격 기준

- 기존 실행의 모든 수치와 25개 테스트가 그대로 통과한다.
- 같은 입력에서 차량·작업 배정과 결과가 완전히 결정론적이다.
- 한 차량의 busy 구간이 겹치지 않는다.
- 배차 시점이 아니라 픽업 시점의 실제 재고에서만 자전거를 차감한다.
- 픽업 후 공급지 재고는 donor reserve 7 미만이 되지 않는다.
- 접근거리·적재거리·총거리와 시간 분해 합이 일치한다.
- 사용자 이동 중·재배치 중·대여소 자전거의 보존식 잔차가 0이다.
- 차량 수가 적다는 이유만으로 정책 intent를 숨기지 않고 미실행 건수를 기록한다.
- P0·기존 P2-R·fleet 1·2·3이 같은 요청 키를 사용한다.
- 결과 CSV·JSON·Markdown·PNG가 재현 가능하게 생성된다.
- `scripts/verify.ps1`이 통과한다.

## 10. 구현 경계와 중단 조건

- 새 dependency, OR-Tools, 실제 VRP 최적화는 추가하지 않는다.
- 정책의 수요처·공급지 선택 순서와 donor reserve 7을 바꾸지 않는다.
- 실제 서울시 차량 수, 차고지, 인건비라고 주장하지 않는다.
- fleet 구현이 기존 재생 엔진을 광범위하게 복제해야 하면 먼저 공통 이벤트 처리 경계를
  재설계하고 별도 목표로 분리한다.
- 공식 depot·교대 데이터가 필요한 현장 비용 추정은 사용자 또는 외부 데이터 확인 전 중단한다.
- 같은 불변조건 실패가 3회 반복되면 구현을 멈추고 원인과 최소 재현을 인계한다.

## 11. 구현 순서

1. 소형 3개 대여소에서 접근·픽업·배송·차량 연속 위치 테스트를 먼저 작성한다.
2. 결정론적 medoid 초기화와 fleet 상태를 구현한다.
3. P2-R transfer intent를 fleet 실행 이벤트로 변환한다.
4. 거리·시간·취소·가동률 지표와 불변조건을 추가한다.
5. 소형 테스트 통과 후에만 5일 사후 민감도를 실행한다.
6. 기존 즉시 출발 결과와 fleet 1·2·3 범위를 함께 보고한다.

## 12. 현재 구현 증거

- `FleetExecutionConfig`가 정책과 좌표·reserve·용량·속도·거리·처리시간 일치를 검사한다.
- `select_greedy_medoids`가 입력 순서와 무관한 합성 초기 위치를 만든다.
- `simulate_replay(..., fleet_config=...)`만 차량 분기를 활성화해 기존 실행을 보존한다.
- trace에 `vehicle_dispatch`, `relocation_out`, `relocation_in`, 차량·작업 ID를 기록한다.
- 접근 중 공급지 대여 후 부분 픽업, busy 차량 미배차, 배송 후 연속 위치를 소형 테스트로 검증했다.
- 전체 검증은 기존 25개와 신규 4개를 합쳐 pytest 29개가 통과했다.
- 165개 대여소·5일 fleet 실데이터는 아직 실행하지 않았다.
