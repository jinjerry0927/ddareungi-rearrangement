# 잠재수요 생성 계약 v2

## 상태와 목적

- 상태: v2 manifest·선택적 시뮬레이터 통합 소형 게이트 PASS
- 분석 등급: `post_hoc_latent_demand_sensitivity`
- 대상: 2025년 11월 강남구 관측수요 재생 시뮬레이터
- 목적: 자전거가 없어서 공개 대여이력에 남지 않은 **직접 미충족 대여수요**가 정책 비교를
  얼마나 바꾸는지 낮음·기준·높음 범위로 측정

잠재수요는 관측값 복원이 아니라 반사실 가정이다. 관측수요 결과를 대체하지 않고 별도
민감도로만 추가하며, 현장 수요나 실제 정책 효과라고 표현하지 않는다.

## 결정 요약

v2는 대여소별 비동질 Poisson 도착과 시간별 재고 스냅샷의 검열 구간을 결합한다. 강도는
학습기간의 비품절 관측시간에서만 추정하고, 평가기간의 재고 스냅샷은 합성 위치와 시간의
검열 증거로만 사용한다. 하나의 최대 요청열을 먼저 만든 뒤 낮음·기준·높음 시나리오가 그
부분집합을 사용하므로 `low ⊆ base ⊆ high`가 항상 성립한다.

v1 실데이터 smoke에서 학습 p95를 실현건수 하드 상한으로 직접 사용하자 3.59% 구간에서
정상적인 Poisson 꼬리까지 잘렸다. 사용자 확인을 받아 v2는 p95를 **시간당 강도 경계**로만
사용하고, 실현건수 하드 상한은 해당 high 검열노출의 Poisson 99백분위수 이상으로 분리한다.

평가 정책의 시뮬레이션 재고가 0인지 여부로 합성 요청을 만들지 않는다. 그렇게 하면 정책마다
다른 수요를 보게 되어 비교가 내생적으로 바뀐다. 모든 정책은 정책 실행 전에 생성·해시한 같은
요청열과 같은 초기 재고를 사용한다.

## 선택 근거와 보류한 대안

공유 모빌리티에서 이용 기록은 공급 가용성에 의해 검열되므로 완료된 여행만으로 수요를
추정하면 편향될 수 있다. 초기 대여소형 연구에서 시간대별 도착을 Poisson 과정으로 보고,
관측 여행을 자전거가 있었던 시간 비율로 보정한 방법이 사용됐다. 최근 연구는 이용자가 가까운
다른 자전거를 선택하는 공간 상호작용까지 모델링한다.

현재 데이터는 한 시간 간격 재고만 있고 이용자의 검색·도보·포기 행동은 없다. 따라서 v2는
해석 가능하고 재현 가능한 Poisson 민감도를 채택하고 다음을 보류한다.

| 후보 | 결정 | 이유 |
|---|---|---|
| 관측 대여에 단일 배수 적용 | 기각 | 품절 노출시간과 무관하고 상한 근거가 없음 |
| 정책별 재고가 0일 때 즉석 생성 | 기각 | 정책마다 다른 수요를 만들어 paired comparison을 위반 |
| 인근 대여소 관측량을 원 대여소 잠재수요로 복사 | 기각 | 실제 대체 이용과 신규 수요를 중복 집계할 수 있음 |
| 검열 Gaussian Process 또는 공간 선택 EM | 후속 연구 | 더 정교하지만 시간별 재고와 행동자료만으로 식별 가정이 큼 |
| 검열 노출시간 기반 Poisson 민감도 | v1 채택 | 현재 데이터로 감사·재현 가능하며 범위 해석이 명확 |

v1 합성 요청은 “원래 대여소에 자전거가 있었다면 발생했을 여행”만 뜻한다. 다른 대여소로
걸어간 대체수요는 모델링하지 않으므로 네트워크 전체 잠재수요의 완전한 추정치가 아니다.

## 데이터 경계와 사전 감사

모든 시각은 서울 현지시각이며 종료 시각은 exclusive다.

- 강도·상한·OD·이용시간 학습: `2025-11-03 00:00 <= t < 2025-11-22 00:00`
- 완충기간: 2025-11-22~23, 학습과 평가 모두에서 제외
- 민감도 평가: `2025-11-24 00:00 <= t < 2025-11-29 00:00`
- 분석 대상: `actionable=true`, 해당 시각과 다음 시각 모두 `inventory_observed=true`
- 원자 구간: 정확히 60분 차이인 `[t, t+1h)` 대여소 구간

2026-08-21 읽기 전용 감사 결과는 다음과 같다.

| 감사 항목 | 결과 |
|---|---:|
| 학습 대여소-시간 구간 | 76,152 |
| 양 끝 재고가 모두 1대 이상인 학습 구간 | 64,916 (85.25%) |
| 대여소×주말여부×시각 비품절 셀 | 7,949 |
| 비품절 표본이 3시간 이상인 셀 | 7,249 (91.19%) |
| 셀별 비품절 표본 중앙값 | 4시간 |
| 평가 검열 원자 구간 | 2,142 |
| 양 끝이 모두 0인 평가 구간 | 1,388 |
| 한쪽 끝만 0인 평가 구간 | 754 |

한 시간 사이의 실제 재고 경로는 관측되지 않는다. 양 끝이 0이어도 중간에 반납 후 재품절됐을
수 있고, 한쪽만 0이면 품절 전환 시각을 알 수 없다. 아래 세 수준은 이 해상도 불확실성을
숨기지 않기 위한 민감도 가정이다.

## 검열 구간 계약

각 원자 구간 `[t, t+1h)`의 양 끝 재고로 합성 가능한 시간집합을 정한다. `q`는 low 15분,
base 30분, high 45분이다.

| `bikes(t)` | `bikes(t+1h)` | 합성 가능한 시간집합 |
|---:|---:|---|
| 1 이상 | 1 이상 | 없음 |
| 1 이상 | 0 | 구간의 마지막 `q`분 |
| 0 | 1 이상 | 구간의 첫 `q`분 |
| 0 | 0 | 60분 전체, 세 수준 동일 |

15·30·45분은 관측 간격 60분 안에서 품절 전환시각이 균등하다는 단순 가정의 25·50·75%
지점이다. 결측 끝점, 60분이 아닌 간격, `actionable=false` 구간에는 합성하지 않는다. 평가 종료
경계의 `t+1h` 스냅샷은 구간 분류에만 사용하고 요청 시각은 평가 범위를 벗어나지 않는다.

## 도착 강도 계약

학습 원자 구간 중 양 끝 재고가 모두 1대 이상인 구간만 비검열 노출시간으로 사용한다. 셀
`g`의 시간당 강도는 다음처럼 계산한다.

```text
lambda_g = 비검열 구간의 관측 대여 건수 합 / 비검열 노출시간 합
```

현재 원자 구간은 한 시간이므로 분모는 구간 수와 같다. 표본 부족 때는 아래 순서로 최초의
표본 3시간 이상인 pool을 사용한다. 3시간은 서로 다른 학습 노출을 최소 세 번 확인하기 위한
사전 고정 기준이며, 평가 결과로 바꾸지 않는다.

1. 대여소 × 주말여부 × 시각
2. 대여소 × 주말여부 × 3시간 블록 (`hour // 3`)
3. 대여소 × 시각
4. 대여소 × 3시간 블록
5. 강남구 × 주말여부 × 시각

각 합성 요청에는 사용한 `intensity_pool`과 학습 노출시간을 기록한다. 마지막 강남구 pool을
사용한 평가 구간 비율이 5%를 넘으면 실데이터 정책 비교를 중단하고 모형을 재검토한다.

### 강도 경계와 실현건수 하드 상한

강도 계산에 선택된 같은 학습 pool의 시간별 관측 대여 건수에서 nearest-rank 95백분위수를
구하고 최소 1건/시간으로 둔다. 원시 평균 강도 `lambda_raw`와 경험적 경계 `p95_g`로 실제
생성 강도를 다음처럼 정한다.

```text
lambda_g = min(lambda_raw, p95_g)
mu_high = lambda_g * high 검열노출시간
hard_cap_g = max(p95_g, PoissonQuantile(0.99, mu_high))
```

`p95_g`는 학습 이상치가 평균 강도를 과도하게 올리는 것을 막고, Poisson 99백분위수는 정상
확률 변동을 실현건수 상한이 자르지 않게 한다. 최대 시나리오 후보가 `hard_cap_g`를 넘으면
요청 키로 만든 안정적인 `cap_rank`가 작은 요청만 남긴 뒤 세 수준을 나눈다. 따라서 상한 뒤에도
중첩 관계가 유지된다.

강도 clipping 구간, 하드 상한 도달 구간, 제거 요청 수를 각각 보고한다. 평가 구간의 1% 이상이
하드 상한에 도달하면 Poisson 꼬리나 구현 경계에 결과가 민감하다는 뜻이므로 정책 권고를
중단한다.

## 요청열과 난수 계약

각 대여소-원자 구간의 high 시간집합에서 시간당 `lambda_g`인 동질 Poisson 점과정을 먼저
만든다. 생성된 시각을 low·base 시간집합으로 필터링해 부분집합을 얻는다.

- 단일 smoke seed: `20251124`
- 최종 paired experiment: `20251124`부터 `20251173`까지 사전 고정한 50개 seed
- 난수 키: `SHA-256(experiment_seed | station_id | interval_start | stream_name)`
- Python의 프로세스별 `hash()`와 입력 행 순서에 의존하지 않음
- 도착시각, 상한순위, OD 표본은 서로 다른 `stream_name` 사용
- 정책 실행 전 `request_manifest_hash`를 계산하고 모든 정책에서 일치 여부를 fail-closed 검증

동일 seed에서 입력 행을 재정렬해도 바이트 단위로 같은 요청 manifest가 나와야 한다. seed가
다르면 확률 표본만 달라지고 학습 pool·강도·상한·검열 구간은 바뀌지 않는다.

## 요청 데이터 계약

기존 정수 `trip_id`만으로는 출처가 드러나지 않으므로 잠재수요 모드에서는 문자열 ID를 쓴다.

| 필드 | 관측 요청 | 합성 요청 |
|---|---|---|
| `request_id` | `obs:{processed_row_index:09d}` | `syn:{seed}:{station}:{interval}:{ordinal}` |
| `source` | `observed` | `synthetic_latent` |
| `latent_min_scenario` | null | `low`, `base`, `high` 중 최초 포함 수준 |
| `rental_at` | 공개 대여시각 | Poisson 후보시각 |
| `return_at` | 공개 반납시각 | `rental_at + sampled_duration` |
| `origin_station_id` | 공개 대여소 | 검열 증거 대여소 |
| `destination_station_id` | 공개 반납소 | 학습 여행 tuple에서 표본 |
| `generation_seed` | null | 고정 experiment seed |
| `censor_interval_id` | null | `{station}:{interval_start}` |
| `intensity_pool` | null | 실제 사용한 backoff pool |
| `raw_hourly_intensity` | null | 학습 pool의 원시 시간당 평균 |
| `hourly_intensity` | null | p95 경계를 적용한 생성 강도 |
| `empirical_p95_per_hour` | null | 학습 pool의 시간당 p95 경계 |
| `poisson_q99_high_window` | null | high 검열노출의 Poisson 99백분위수 |
| `hard_count_cap` | null | p95와 Poisson q99 중 큰 실현건수 상한 |

관측 ID의 행 인덱스는 정제 Parquet 전체에 인덱스를 먼저 부여한 뒤 기간·대여소를 필터링한다.
관측행은 원본 필드와 값을 바꾸지 않는다. 합성행은 별도 manifest로 저장한 뒤 실행 직전에
결합하며, 원본 Parquet에 덮어쓰지 않는다.

## 목적지·이용시간·반납 계약

합성 요청이 공급됐다면 어디로 얼마나 이용했을지 보존하기 위해 학습기간의 완료 여행 한 행을
복원추출하고 `(destination_station_id, duration_minutes)`를 함께 사용한다. 둘을 따로 뽑지 않아
OD와 이용시간의 결합을 유지한다. 유효 표본은 반납시각이 있고 이용시간이 양수인 관측 여행이다.

표본 pool은 다음 순서로 최초의 20건 이상인 항목을 사용한다.

1. 출발 대여소 × 주말여부 × 시각
2. 출발 대여소 × 주말여부 × 3시간 블록
3. 출발 대여소 전체 학습 여행
4. 강남구 × 주말여부 × 시각

20건은 경험적 tuple 분포가 극소수 여행에 좌우되지 않게 하는 사전 고정 최소치다. 실제 선택한
`trip_pool`을 요청행에 기록한다. 목적지가 시뮬레이션 범위 밖이면 성공 대여 시 강남구 유출로
처리하고, 범위 안이면 성공했을 때만 조건부 반납 이벤트를 만든다.

- 합성 대여 실패: 자전거 감소 없음, 합성 반납 없음
- 합성 대여 성공·내부 목적지·평가기간 내 반납: 조건부 내부 반납 1대
- 합성 대여 성공·외부 목적지: 외부 유출 1대
- 합성 대여 성공·평가 종료 뒤 내부 반납: 종료 시점 내부 운행 중 1대
- 외부에서 시작하는 합성 무조건 반납은 만들지 않음

## 자전거 보존식

출처별 카운터를 따로 보관하고 총계에서 다음 식의 잔차가 항상 0이어야 한다.

```text
초기 대여소 재고
+ 관측 무조건 외부유입 반납
- 관측 성공 외부유출 대여
- 합성 성공 외부유출 대여
- 종료 시 관측 내부 운행 중
- 종료 시 합성 내부 운행 중
- 종료 시 재배치 차량 적재 중
- 최종 대여소 재고
= 0
```

내부에서 성공해 평가기간 안에 돌아온 관측·합성 여행은 출발과 반납이 상쇄된다. 출처별 합과
전체 합이 모두 일치해야 하며 하나라도 다르면 산출물을 만들지 않는다.

## 지표와 보고 계약

기존 관측수요 기본 실행은 결과가 바뀌면 안 된다. 잠재수요 모드만 다음 지표를 추가한다.

- `observed_requests`, `observed_successful_rentals`, `observed_failed_rentals`, `observed_service_rate`
- `synthetic_requests`, `synthetic_successful_rentals`, `synthetic_failed_rentals`, `synthetic_service_rate`
- `combined_requests`, `combined_successful_rentals`, `combined_failed_rentals`, `combined_service_rate`
- 시나리오·seed·요청 manifest hash·pool backoff·상한 도달 감사값
- 대여소별 같은 출처 분해와 p10 서비스율

`combined_*`를 관측 실적이라고 부르지 않는다. 정책별 보고서는 먼저 관측수요 결과, 다음에
잠재수요 범위를 표시한다. 모든 정책-시나리오-seed 조합은 같은 manifest hash를 확인한 뒤에만
paired 차이와 95% bootstrap 신뢰구간을 계산한다.

## 누수 방지와 실험 해석

- 강도·상한·backoff·OD·이용시간은 학습기간만 사용한다.
- 평가기간 재고는 검열 시간집합을 표시하는 입력일 뿐 모수 적합이나 정책 선택에 쓰지 않는다.
- low/base/high와 50개 seed는 정책 결과를 보기 전에 이 문서로 동결한다.
- 평가 서비스율·형평성·거리 결과로 생성 규칙을 재튜닝하지 않는다.
- 규칙 변경은 `contract_version`을 올리고 새 미사용 기간에서 다시 평가한다.
- 같은 5일 홀드아웃을 이미 정책·fleet 분석에 썼으므로 결과는 독립 검증이 아닌 사후 민감도다.

현재 계약의 기대값 투영은 low 1,297건, base 1,567건, high 1,829건이며 기존 16,205개 관측
요청의 약 8.0%, 9.7%, 11.3%다. 이는 생성기 구현 전 규모 점검일 뿐 정책 효과 결과가 아니다.
단일 잠재수요 값을 고르지 않고 세 수준 전체를 보고해야 하는 이유다.

### v1 실패와 v2 실데이터 manifest 게이트

2026-08-21에 165개 대여소와 smoke seed `20251124`로 정책 실행 없이 manifest만 메모리에서
생성했다.

| 검사 | 결과 | 판정 |
|---|---:|---|
| low / base / high 요청 | 1,303 / 1,591 / 1,878건 | 중첩 PASS |
| 최종 강남구 intensity backoff | 12 / 2,142구간 (0.56%) | 5% 이하 PASS |
| 경험적 p95 상한 도달 | 77 / 2,142구간 (3.59%) | 1% 이하 FAIL |
| 상한으로 제거된 후보 | 101건 | 재검토 필요 |
| master manifest SHA-256 | `cd61d9a4886b088f5ad1bcfcd73feb51bf7611b4f71b009427f6f339fb7a42bf` | 재현 기준 |

p95 하드 상한은 Poisson 과정에서 자연스럽게 발생하는 상위 꼬리까지 자를 수 있다. 계약의
중단 기준에 따라 시뮬레이터 통합과 정책 batch를 실행하지 않는다. 상한을 바꾸려면 계약 버전을
올리고 사용자 확인을 받은 뒤 같은 소형·실데이터 manifest 게이트를 다시 통과해야 한다.

사용자 확인 후 2026-08-31에 v2 상한을 구현하고 같은 165개 대여소·seed로 다시 검증했다.

| 검사 | v2 결과 | 판정 |
|---|---:|---|
| low / base / high 요청 | 1,382 / 1,673 / 1,964건 | 중첩 PASS |
| 최종 강남구 intensity backoff | 12 / 2,142구간 (0.56%) | 5% 이하 PASS |
| p95 강도 clipping | 0 / 2,142구간 (0.00%) | 감사 완료 |
| Poisson q99 하드 상한 도달 | 13 / 2,142구간 (0.61%) | 1% 미만 PASS |
| 하드 상한으로 제거된 후보 | 15 / 1,979건 | 감사 완료 |
| master manifest SHA-256 | `d403dbf1f8fab9a8a32f3e8fe83a120f81fcac4042acbc641eda092864c55375` | 재현 기준 |

v2는 v1이 제거한 정상 꼬리의 대부분을 복원하면서 사전 품질 게이트를 통과했다. 이 수치는
잠재수요 manifest 결과이며 정책 효과 결과는 아니다.

### 선택적 시뮬레이터 통합 게이트

2026-08-31에 manifest와 해당 SHA-256을 반드시 함께 받는 선택적 통합을 구현했다. 입력 hash는
이벤트 생성 전에 재계산하며 불일치, 필수값 결측, 중복 `request_id`, `synthetic_latent`가 아닌
출처, 평가구간 밖 요청, 범위 밖 출발 대여소는 fail-closed 처리한다.

manifest가 없는 관측 전용 실행은 기존 `SimulationMetrics`, 대여소 지표, trace 열을 그대로
유지한다. manifest 실행만 `SourceDemandMetrics`와 `source_station_metrics`를 추가하고 trace에
`request_id`, `request_source`를 덧붙인다. 호환성을 위해 기존 `SimulationMetrics` 필드명은
바꾸지 않으므로 잠재수요 실행의 정확한 출처 해석에는 side-car 지표를 사용한다.

소형 통합 사례에서 관측 1건과 합성 2건을 재생했다. 합성 1건은 성공 후 내부 반납했고, 같은
출발지의 다음 합성 1건은 재고 0으로 실패해 예정 반납이 억제됐다. 관측·합성·combined
trip-flow 잔차와 전체 자전거 보존식 잔차는 모두 0이었고, hash 변조 입력은 실행 전에
거부됐다. 기존 39개 테스트와 신규 3개를 합친 전체 42개 테스트가 통과했다.

### 50-seed 정책 민감도 결과

2026-08-31에 동결 seed 50개, 세 수준, P0·P2-R의 300개 실행을 완료했다. P2-R은 donor
reserve 7, 시간당 최대 3회, 평균속도 20km/h, 적재 10대인 즉시출발 정책이다.

| 수준 | 합성요청 평균 (범위) | combined 실패 방지 평균 (95% CI) | 관측 실패 방지 평균 | p10 변화 평균 | 악화 대여소 평균 |
|---|---:|---:|---:|---:|---:|
| low | 1,368.2 (1,291~1,451) | 1,509.0 (1,499.0~1,518.8) | 933.9 | +32.468%p | 16.3 |
| base | 1,644.6 (1,564~1,732) | 1,517.6 (1,507.8~1,527.7) | 899.5 | +30.060%p | 17.2 |
| high | 1,922.4 (1,839~2,039) | 1,531.8 (1,521.3~1,542.5) | 882.2 | +27.679%p | 18.0 |

정책 우열·관측/combined 개선 부호·p10·악화 대여소 존재 여부는 모든 seed와 수준에서 기존
관측 기준과 같은 방향이었다. 최종 backoff 최대 0.56%, 하드 상한 도달 최대 0.65%, 합성요청
비중 최대 12.58%로 각각 5%·1%·25% 중단선 아래였다. 7개 사전 중단조건은 모두 PASS다.

잠재요청이 늘수록 combined 실패 방지는 유지됐지만 기존 관측요청 실패 방지는 감소하고 악화
대여소는 늘었다. 이는 P2-R 효과가 사라진다는 뜻이 아니라, 추가 수요와 기존 수요가 같은
재고를 경쟁해 편익 배분이 달라진다는 뜻이다. 결과는 실제 잠재수요나 인과효과 추정치가 아니다.

## 구현 합격 기준

다음 조건을 모두 통과하기 전에는 165개 대여소·5일 정책 batch를 실행하지 않는다.

1. 비품절·결측·비60분 구간에서 합성 요청이 0건인 소형 테스트
2. `low ⊆ base ⊆ high` ID 집합과 입력 재정렬 불변 테스트
3. 같은 seed 재실행 동일, 다른 seed 표본 변화 테스트
4. 관측·합성 ID namespace와 출처별 지표 합계 테스트
5. 합성 실패에는 반납이 없고 성공 내부여행에만 반납이 있는 테스트
6. 기존 전체 39개 테스트와 관측 전용 핵심 홀드아웃 수치 무변경 회귀 테스트
7. 출처별·전체 자전거 보존식 잔차 0 테스트
8. 정책별 manifest hash 불일치 시 fail-closed 테스트
9. 실제 평가 입력의 마지막 강남구 pool 사용률 5% 이하
10. `ruff check`, `ruff format --check`, `pytest`, `scripts/verify.ps1` 통과

## 중단·인계 기준

생성기와 시뮬레이터 통합은 이 v2 계약 안에서만 진행할 수 있다. 다음 중 하나면 정책 결론을
내리지 않고 사용자에게 인계한다.

- low/base/high에서 P0와 P2-R의 우열 방향이나 정책 순위가 바뀜
- 관측수요 개선과 combined 개선의 부호가 다름
- 최악 10% 서비스율 또는 악화 대여소 결론의 방향이 시나리오별로 바뀜
- 강남구 최종 backoff가 평가 검열 구간의 5% 초과
- Poisson q99 하드 상한 도달 구간이 평가 검열 구간의 1% 이상
- 합성 요청 기대량 또는 실현량이 관측 요청의 25% 초과
- 인근 대여소 대체행동, 검열 창, 상한, seed 집합을 바꿔야 함

방향이 모든 수준과 seed에서 유지돼도 “실제 수요를 복원했다”고 결론내리지 않는다. 더 강한
주장을 하려면 더 촘촘한 재고 로그, 앱 검색·실패 로그 또는 현장실험이 필요하다.
